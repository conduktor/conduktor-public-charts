# AGENTS.md

Guidance for AI coding agents working on this repository. Humans should start with [CONTRIBUTING.md](CONTRIBUTING.md).

## Repository overview

Public Helm charts for Conduktor products, published at `https://helm.conduktor.io`.

| Chart directory      | Chart name          | Product                                   |
|----------------------|---------------------|-------------------------------------------|
| `charts/console`     | `console`           | Conduktor Console (+ Cortex monitoring)   |
| `charts/gateway`     | `conduktor-gateway` | Conduktor Gateway (Kafka proxy)           |
| `charts/provisioner` | `provisioner`       | Conduktor CLI provisioning Job / CronJob  |

All charts depend on the Bitnami `common` library chart (`common.*` helpers).

```
charts/<chart>/
├── Chart.yaml           # version (chart) + appVersion (product)
├── values.yaml          # source of truth, annotated with readme-generator `## @param` comments
├── values.schema.json   # GENERATED from values.yaml by `make generate-readme`
├── README.md            # parameter tables GENERATED by `make generate-readme`
├── templates/           # _helpers.tpl, NOTES.txt, tests/ (helm test hooks)
└── ci/                  # test-config.yaml + NN-<name>-values.yaml test scenarios
test/                    # Python test runner (python -m test.runner), see test/README.md
k3d/                     # local k3d cluster config and fixtures
```

## Golden rules

1. **No breaking changes by default.** Users upgrade with `helm upgrade` and their existing values. Every change must keep existing values files rendering the same resources with the same behaviour, unless the user explicitly asks for a breaking change. See [Backward compatibility](#backward-compatibility).
2. **`values.yaml` is the API.** Every value is documented with a `## @param` comment, then `make generate-readme` regenerates `README.md` and `values.schema.json`. Never hand-edit the generated parameter tables or the schema.
3. **Test what you change.** Run the [validation loop](#validation-loop) before reporting a task as done. Cover new behaviour with a `ci/` scenario.
4. **Do not bump `Chart.yaml` `version`** for regular changes: the release workflow (`.github/workflows/create-release.yaml`) does it. `appVersion` and image tag bumps come from automated PRs too.
5. **Only use local clusters.** Install charts only in the k3d cluster (`k3d-conduktor-platform`), always passing `--kube-context` / `--context` explicitly. Never touch a remote cluster.
6. Follow [Conventional Commits](https://www.conventionalcommits.org/) scoped by chart: `fix(console): ...`, `feat(gateway): ...`.

## Tooling

The dev environment comes from `shell.nix` (loaded by direnv through `.envrc`): `helm`, `k3d`, `kubeconform`, `pre-commit` and Python with `click`, `pydantic`, `pyyaml`. If it isn't loaded (`$IN_NIX_SHELL` empty), wrap commands: `nix-shell --run '<cmd>'`. Without Nix: `pip install -r test/requirements.txt`, plus `ct` (chart-testing), `yq` and `readme-generator` (`make install-readme-generator`).

Chart dependencies must be pulled once (and again after a `Chart.yaml` dependency change). `charts/*/charts/` is gitignored:

```shell
make helm-deps                                    # helm repo add/update
for c in charts/*/; do helm dependency build "$c"; done
```

`make help` lists every target.

## Validation loop

Run from fastest to slowest and stop at the first failure. Steps 1 to 5 need no cluster.

### 1. Lint

```shell
helm lint charts/gateway
helm lint charts/provisioner
# console requires mandatory values
helm lint charts/console --set config.organization.name=test,config.admin.email=test@test.io,config.admin.password=test,config.database.password=test,config.database.username=test,config.database.host=test

# Same lint as CI (chart-testing: Chart.yaml schema, yamllint, every ci/*-values.yaml)
ct lint --config .github/ct-lint-config.yaml --charts charts/<chart>
```

### 2. Render templates

```shell
helm template t charts/<chart> -f charts/<chart>/ci/<scenario>-values.yaml
# Render one template only
helm template t charts/<chart> -f <values> --show-only templates/deployment.yaml
# Debug a template error
helm template t charts/<chart> -f <values> --debug
# Check a value combination that must fail with a clear message
helm template t charts/<chart> --set foo.bar=invalid; echo "exit=$?"
```

### 3. Validate manifests against the Kubernetes schemas

```shell
make lint-manifests                                        # all charts, every ci scenario
python -m test.runner lint-manifests --chart <chart>       # one chart
helm template t charts/<chart> -f <values> | kubeconform -strict -ignore-missing-schemas -summary
```

### 4. Check backward compatibility: render diff against `main`

Render the chart from `main` and from your working tree with the **same values** and compare. With an existing values file, any diff other than the intended one is a potential breaking change.

```shell
CHART=gateway; VALUES=charts/$CHART/ci/01-basic-gateway-required-values.yaml
BASE=$(mktemp -d)
git archive main charts/$CHART | tar -x -C "$BASE"
helm dependency build "$BASE/charts/$CHART" >/dev/null
diff -u <(helm template t "$BASE/charts/$CHART" -f "$VALUES") \
        <(helm template t "charts/$CHART" -f "$VALUES")
```

Run it for every `ci/*-values.yaml` of the chart, and with default values when the chart renders without any. Randomly generated values (`randAlphaNum` passwords, self-signed certificates) and their `checksum/*` annotations differ on every render: ignore them, or set them explicitly in a temporary values file.

To compare against the last **released** version instead of `main`:

```shell
helm template t conduktor/<chart-name> --version <released-version> -f "$VALUES"
```

### 5. Regenerate docs and run pre-commit

```shell
make generate-readme             # README.md + values.schema.json from values.yaml
pre-commit run --all-files       # yaml checks, gitleaks, helm lint, readme generation
git diff --stat                  # generated files must be part of the change
```

CI fails if `README.md` is not up to date with `values.yaml`.

### 6. Install and test on a local k3d cluster

Slow (several minutes per scenario). Run it for changes to runtime behaviour: probes, env vars, volumes, TLS, services, upgrades. Some gateway scenarios need a license in `CDK_LICENSE`.

```shell
make k3d-up                                                 # cluster + ingress-nginx + cert-manager
make test-run CHART=<chart> SCENARIO=<NN-name>              # previous release -> current upgrade path + helm test
make test-run CHART=<chart> SCENARIO=<NN-name> SKIP_UPGRADE=1   # fresh install only
make test-changed                                           # every chart changed vs main
make test-install CHART=<chart> SCENARIO=<NN-name>          # keep it installed to inspect
kubectl --context k3d-conduktor-platform get pods -n ct-<chart>-<NN-name>
make test-uninstall CHART=<chart> SCENARIO=<NN-name>
make k3d-down
```

The default `run` path installs the **previous released version** with the previous values, upgrades to the current chart, then switches to the current values, running `helm test` at each step. A failure in the upgrade steps means a breaking change. See [test/README.md](test/README.md) for scenario conventions (`db_<NN>` database, `bucket-<NN>` bucket, dependency service URLs).

### Which checks for which change

| Change                                         | Minimum checks                     |
|------------------------------------------------|------------------------------------|
| Docs, comments, `values.yaml` descriptions     | 5                                  |
| Template or helper change                      | 1, 2, 3, 4, 5                      |
| New value / feature                            | 1 to 5, plus a new `ci/` scenario  |
| Probes, env, volumes, services, TLS, upgrades  | 1 to 6                             |
| Dependency version (`Chart.yaml`)              | 1 to 6                             |

## Backward compatibility

Every chart is installed by customers who run `helm upgrade` with values written for older versions. By default, a change **must not**:

- Remove or rename a value, or change its type or the meaning of its default.
- Change a default in a way that alters an existing deployment (new port, different storage, feature enabled or disabled, different resource names).
- Rename resources or change `metadata.name` (helpers like `*.fullname`): it causes delete/recreate, data loss for PVCs and broken references from user resources.
- Change immutable fields of existing resources: `spec.selector` / `matchLabels` of Deployments and StatefulSets, `volumeClaimTemplates`, Service `clusterIP`, Job templates. `helm upgrade` fails on them.
- Change label selectors used by users' NetworkPolicies, ServiceMonitors or Services.
- Make `values.schema.json` stricter so that previously valid values get rejected.
- Raise the minimum Kubernetes or Helm version, or bump a dependency major version (the `common` chart is pinned on purpose, see `Chart.yaml`).

Techniques to evolve without breaking:

- **Additive changes**: new values default to the current behaviour (feature off, same port, same name).
- **Deprecate, don't remove**: keep reading the old key, give precedence to the new one, and warn in `NOTES.txt`. Existing patterns:
  - Fallback helpers in `charts/gateway/templates/_helpers.tpl` (e.g. `tls.keystore.secretRef` over the deprecated `tls.secretRef`).
  - `conduktor-gateway.deprecationBanner` in `charts/gateway/templates/NOTES.txt`.
  - Console: migration of the deprecated `host`/`port` to the `hosts` list in `charts/console/templates/_helpers.tpl`.
- Mark deprecated values in `values.yaml` (`## @param old.key (deprecated) Use new.key instead`) and keep a `ci/` scenario that uses the legacy form (e.g. `charts/gateway/ci/10-legacy-portrange-values.yaml`).
- Use `fail` / `required` only for configurations that would never work, with an actionable message naming the values to set.

When a breaking change is unavoidable or explicitly requested, say so in the PR: what breaks, who is affected, the migration steps for `values.yaml`, and the `breaking` label (CI then skips the upgrade test). Ask for confirmation before making one.

## Chart best practices

### Values

- camelCase keys, nested by component (`gateway.*`, `config.*`, `platform.*`). Booleans use `enabled`.
- Every key has a `## @param <path> <description>` comment, with type modifiers when needed (`[array]`, `[object]`, `[string]`, `[nullable]`). Use `## @section` to group values and `## @skip` for values that must not appear in docs.
- Provide sane, working, secure defaults. Use empty values (`""`, `{}`, `[]`) rather than commented-out examples so users can see every option.
- Secrets: always offer an `existingSecret`-style option next to plain values, and never log or echo secret values in `NOTES.txt`.
- Image references are split into `registry` / `repository` / `tag` / `pullPolicy` and honour `global.imageRegistry` and `global.imagePullSecrets`.
- Expose the standard Kubernetes extension points for each workload: `resources`, `nodeSelector`, `tolerations`, `affinity`, `podAnnotations`, `podLabels`, `podSecurityContext`, `containerSecurityContext`, `extraEnvVars`, `extraVolumes`, `extraVolumeMounts`, `serviceAccount.*`.

### Templates

- Reuse the Bitnami `common` helpers (`common.names.fullname`, `common.labels.standard`, `common.labels.matchLabels`, `common.images.image`, `common.tplvalues.render`, `common.secrets.lookup`) and the chart's own `_helpers.tpl` before writing new logic.
- Prefix chart helpers with the chart name (`conduktor-gateway.*`, `conduktor.*`) and document each `define` with a short comment listing its parameters.
- Every resource gets the standard labels plus `commonLabels` / `commonAnnotations`, and is placed in the release namespace (`common.names.namespace`).
- Use `nindent` with `toYaml`, `{{-` / `-}}` to control whitespace, and `quote` for strings that YAML could parse as another type (versions, booleans, numbers in env vars).
- Render user-provided strings that may contain templates with `common.tplvalues.render`.
- Add `checksum/*` pod annotations for ConfigMaps and Secrets the pod depends on, so config changes roll the pods.
- Do not generate random values without `common.secrets.lookup`: otherwise they rotate on every `helm upgrade`.
- Guard optional resources with `{{- if .Values.x.enabled }}` and use `.Capabilities.APIVersions.Has` before rendering CRD-based resources (ServiceMonitor, PrometheusRule, Certificate, GrafanaDashboard).
- Keep `NOTES.txt` useful: access instructions, deprecation warnings, misconfiguration hints.
- Secure by default: non-root, `readOnlyRootFilesystem` when the app supports it, drop capabilities, no privileged containers.

### Tests

- New feature or bugfix: add or extend a scenario `charts/<chart>/ci/NN-<name>-values.yaml` (next free number, `-values.yaml` suffix). It is used by `ct lint`, `make lint-manifests` and `make test-run`.
- Keep `templates/tests/` helm test hooks meaningful (health check against the deployed service).
- Never commit real credentials or licenses: CI injects them through env vars (see `k8s_secrets` in `ci/test-config.yaml`).

## Definition of done

- [ ] No breaking change, or it is explicitly requested, confirmed and documented.
- [ ] Validation loop steps passed for the change type, with the commands and results reported.
- [ ] `make generate-readme` run, generated `README.md` and `values.schema.json` included.
- [ ] New behaviour covered by a `ci/` scenario.
- [ ] Self-review of the diff: no leftover debug output, no commented-out code, no unused values or helpers.
